THE MEASUREMENT
---------------
    list=0x4500fbc  count@8=0x80(128)
    slot=0x0   oldval=0x4500f8c
    slot=0x4   oldval=0x2fffc
    slot=0x8   oldval=0x5ffff
    slot=0xc   oldval=0x70000
    slot=0x10  oldval=0x9000a
    slot=0x14  oldval=0xb0008

`slot` is r31, the pointer setAll walks. It reads 0, 4, 8, 0xc, 0x10, 0x14 --
it is not a pointer at all, it is zero being incremented by 4. r31 comes from
this->[0x14].

So the list has count 128 and a NULL element array, and setAll walks guest
addresses 0,4,8,... treating low-memory bytes as string pointers.

FIELD LAYOUT CONFIRMED AGAINST COMMUNITY WORK
----------------------------------------------
NefariousTechSupport posted the exact layout in #alchemy (2025-04-17):

    class igTDataList : public igContainer {
        int32_t _count;                    // +0x08
        int32_t _capacity;                 // +0x0C
        igMemory::Properties<T> _data;     // +0x10 _flagsAndSize, +0x14 _buffer
    };

count@0x8 and _buffer@0x14 are exactly what this run measured, so the reads
are interpreted correctly and not by guesswork. ("an igStringRefList is an
igDataList" -- same source, #igcauldron 2024-09-07.)

WHERE IT COMES FROM
-------------------
igMemoryPoolFrameManager::initDefault does, in order:

    setCapacity(list, 128, 4)     <- asked for 128 elements of 4 bytes
    setCount(list, 128)
    setAll(list, ref)

So setCapacity IS called, with correct arguments, and _buffer is still NULL
afterwards. Then setCount happily records 128, and setAll walks the void.

WHY RE-MEASURE RATHER THAN ASSUME
----------------------------------
Finding B was measured on 2026-08-28: table=0, index=0. That predates today's
record-form CR0 fix, which changed the outcome of 6,745 branches across the
game, and the divw/divwu guard. Treating a pre-fix measurement as still true
is exactly the mistake that has cost the most time today.

Probe added at 215db94 reporting the vcall result, the table pointer, the
index and the entry.
