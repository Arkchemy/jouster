STATIC ANALYSIS OF WHY

All three registration functions have exactly one call site each in
~8.7M lines of generated C, and it is ppc_dispatch -- the recompiler's
indirect-call dispatcher. No recompiled function calls them directly;
they are reachable only through a function pointer.

Scanning init_globals' literal byte stores for their addresses finds
exactly one table entry: arkRegisterMetaValidate (0x021c39c8) sits at
0x119f08. Reconstructing the words around it shows what that table is:

  0x119ec8: 0x021c2a0c   code
  0x119ecc: 0x021b8cac   code
  0x119ed0: 0x10062b58
  0x119ed8: "_rootElementName"
  0x119eec: "_document"
  0x119ef8: 0x101349b4   .bss slot
  0x119efc: 0x101349b8   .bss slot
  0x119f04: 0x021be158   code
  0x119f08: 0x021c39c8   arkRegisterMetaValidate
  0x119f10: "igRegist[ry]"

That is igRegistry's own meta-object descriptor: field-name strings,
method pointers, and pointers to the .bss slots the registration is
supposed to fill. Those slots sit at 0x101349b4/0x101349b8, in the same
region as the never-written 0x101345e8.

So the metadata is present and correct in .rodata. What is missing is
whatever walks it.

NEXT

The open question is narrow and specific: what invokes the meta
registration? It is an indirect call, so the useful next measurement is
a load-watch (the mirror of g_ppc_watch_store_addr, which does not exist
yet) armed on 0x119f08 -- does anything ever READ the table entry?

  - never read  -> the walk itself never starts; find its trigger.
  - read, not called -> the dispatch fails to resolve, which would be a
    recompiler-side problem rather than an engine-order problem.

Both are cheap to distinguish and neither needs another guess.
