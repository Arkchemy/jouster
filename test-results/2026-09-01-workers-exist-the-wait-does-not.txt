THE QUESTION THE BUILD WAS WRITTEN TO ANSWER
--------------------------------------------
    threads: created=2 started=2      from frame 3,420 onward

Idle workers, not absent ones. Of the two possibilities the counter was
added to separate, it is the first: the job queue has worker threads, they
were created and started at igJobQueue::init, and they are asleep. Every
fix aimed at "no workers were ever created" would have been aimed at
nothing.

WHAT 0x21da168 IS
-----------------
Inside ppc_jqWorkerSleep__4CoreFPQ2_4Core8jqWorker. The call immediately
before it:

    21da158: mr   r6, r26                  low word of the timeout
    21da15c: mr   r5, r25                  high word
    21da160: addi r3, r28, -0x7c68         the OSEvent*
    21da164: bl   0x2589f20                OSWaitEventWithTimeout

r5 and r6 are loaded in the two instructions before the branch. r4 is
never written.

THE BUG, WHICH IS THE ONE FIXED ON 2026-08-30 IN A FILE THAT SWEEP MISSED
-------------------------------------------------------------------------
    cafeos_coreinit_sync.h:261
    int64_t timeout_ticks = ((int64_t)ctx->r[4] << 32) | (int64_t)ctx->r[5];

PPC EABI puts a 64-bit argument in a pair starting on an ODD register, so
with the OSEvent* in r3 the OSTime is in r5:r6. This read r4:r5 -- one
register short, exactly like the four Atomic64 shims fixed at 17:03 that
same day.

The 17:03 write-up stated "the only other 64-bit argument assembled from
registers anywhere in the shims is GX2WaitTimeStamp". That was wrong. The
sweep looked in cafeos_coreinit_atomic.h; this one lives in
cafeos_coreinit_sync.h and was written in an earlier commit
(2ad5e67, the pthread-backed OSMutex/OSEvent work). A grep for `<< 32`
across every shim header finds it in seconds, and finds it is the last
one -- atomic.h is r5:r6 and r7:r8 correctly, OSSleepTicks and
OSTicksToCalendarTime take their 64-bit value as the FIRST argument so
r3:r4 is right for them, and GX2WaitTimeStamp likewise.

AND A SECOND BUG UNDERNEATH IT
-------------------------------
    int64_t ns = (timeout_ticks * 1000000000LL) / ARKCHEMY_ESPRESSO_TIMER_CLOCK;

ticks * 1e9 overflows int64 above ~9.2e9 ticks, which at 62,156,250 Hz is
only about 148 seconds -- inside the range real timeouts actually use.
With the registers as they were:

    read r4:r5   311,539,661,883,310,111 ticks
                 x1e9 wraps to -1,633,196,948,712,425,984
                 -> deadline in the PAST
                 -> pthread_cond_timedwait returns immediately
                 -> break, woke_signaled = 0, return FALSE
                 -> caller loops and calls again, forever

That is the spin, and the arithmetic is exact rather than inferred.

Worth stating plainly: the correct registers do not save it. r5:r6 is
133,145,076,804 ticks (2,142 s), and 133,145,076,804 x 1e9 overflows too,
wrapping positive to ~4.0e18. Right registers, still a garbage deadline.
Both bugs had to be fixed for either to matter.

OSTicksToCalendarTime, twenty lines further down the same file, already
divides first and takes the remainder. The safe pattern was in the file
the whole time.

FIXED (all three)
-----------------
    OSWaitEventWithTimeout  timeout now read from r5:r6
    OSWaitEventWithTimeout  seconds split from remainder before scaling,
                            deadline clamped to one year
    OSSleepTicks            same overflow, same fix (its r3:r4 was right)

Header compiles clean. NOT yet built into an .nro and NOT yet run.

A SEPARATE OBSERVATION, NOT THIS BUG
------------------------------------
The recompiler emits lwarx/stwcx. as a plain load and a plain store with
cr0_eq forced to 1 -- the reservation always "succeeds":

    /* 21da150: stwcx. r0, 0, r31 */
    ppc_store_u32(ctx, 0u + ctx->r[31], ctx->r[0]);
    ctx->cr0_lt = 0; ctx->cr0_gt = 0; ctx->cr0_eq = 1;

That is why these retry loops exit rather than spin, so it is not what
was observed here. But it is an unsynchronised read-modify-write on
memory that real host threads now share -- the same class of defect as
the atomics header, one level lower, in generated code rather than in a
shim. jqWorkerSleep uses it to increment and decrement a waiter count
that two threads touch. Worth its own measurement before it is assumed
harmless.

same afternoon.
