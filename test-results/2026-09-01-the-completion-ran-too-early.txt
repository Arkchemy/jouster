The status is right too. The callback is

    2155b88: cmpwi r30, 1        r30 is the status we passed

The game asked for ONE element of 131072 bytes (sz=131072 cnt=1), the shim
read it and returned elements_read = 1, and the callback took its success
path. Not an accident of ours matching: that is what Cafe OS returns.

THE BUG IS ORDERING, AND IT IS ONE INSTRUCTION WIDE
----------------------------------------------------
igCafeStorageDevice::read(igFileWorkItem*):

    2155cd0: bl   FSReadFileWithPosAsync      <- our shim ran the callback
                                                 INSIDE this call
    2155cd4: stw  r29, 0x1c(r31)              <- the caller writes state
                                                 AFTER the call returns

Cafe OS delivers an FS completion later, on its own I/O thread, after the
call has returned. This shim invoked it inline. So the sequence on hardware
was:

    read() sets up the work item
      FSReadFileWithPosAsync
        igCafeStorageDevice::asyncCallback
          igFileWorkItem::setStatus(...)     item marked complete
          igMemoryPool::free(...)            async block released
      returns
    stw r29, 0x1c(r31)                       caller writes over that state,
                                             storing a pointer to the block
                                             that was just freed

The completion finished the work item before the function that created it
had finished setting it up. The file scheduler then polled a work item whose
state had been overwritten, forever.

cbwork=15 is the number of guest calls the callback made. It is not
suspiciously small -- the function body is short, two virtual dispatches and
three direct calls. It ran fully and correctly. It simply ran too early.

THE FIX
-------
Completions are queued instead of invoked inline, and delivered at the next
import call -- always between guest instructions, and always after the
function that issued the read has returned.

The pump is called from OSLockMutex. While the file scheduler is idle those
are the hot path at roughly 31 calls per frame, so a completion is delivered
within a frame of being queued. cafeos_coreinit_fs.h is included before
cafeos_coreinit_sync.h in every generated translation unit, which is what
makes that call legal.

Re-entrancy is guarded, since a completion callback can itself call a shim
that pumps. The queue is 16 deep and reports overflow rather than dropping
silently:

    asyncq: q=%u done=%u drop=%u pend=%u

WHAT TO EXPECT IF THIS IS RIGHT
-------------------------------
    asyncq q=1 done=1 drop=0        the completion is delivered, once
    ard climbs past 1               the loader asks for the rest of the file
    fs read total -> 198,695        bootstrap.bld is finished, not abandoned
    open= climbs past 2             bootstrap_lang.bld is the documented next
                                    file in the boot order

If ard stays at 1 with done=1, the completion is being delivered and the
loader still is not advancing, and the fault is inside the work-item state
machine rather than in the ordering.

WHAT IS NOT ESTABLISHED
-----------------------
That OSLockMutex is the right delivery point rather than merely a workable
one. Real Cafe OS delivers on a dedicated I/O thread; this delivers on
whichever guest thread next takes a mutex. That is closer to correct than
inline delivery and is not the same as correct. If the work item is expected
to complete on a specific thread, this will need revisiting.
