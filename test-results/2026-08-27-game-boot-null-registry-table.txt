TWO INDEPENDENT FAILURES, NOT ONE

1. Static initialiser 87 exhausts the ExpHeap.

   Every allocation event in the static-init phase carries sti_idx=87,
   last_pc=0x2583420, caller_lr=0x257f2d8, and requested=131072 exactly.
   The DEFHEAP arena is reported spent (heap_used=0 against a 1,040MB
   region) and each 128KB request falls through to the ExpHeap at
   0x4000000, which climbs 131,136 -> 5,245,440 across 40 logged events
   before suppression, and is later found full at heap_used=121,563,072
   of 121,634,816. That is roughly 927 allocations of 128KB from one
   initialiser, all from the same call site, none of them freed. This is
   the same "MEM2 fills to ~100% at every size from 32MB to 928MB"
   behaviour recorded on 24 Aug, now pinned to a single initialiser and
   a single call site rather than to a size.

2. The registry table itself is NULL -- not an unregistered entry in it.

   This is a correction to the 2026-08-24 (cont. 50) conclusion, which
   read the fault as "a NULL entry in a global registry" and asked for a
   build that logs the table base and index so the missing entry could
   be named. This is that build, and it names them:

     NULL REGISTRY ENTRY: table=0x0  index=0  byteoff=0  caller_lr=0x215DBC0

   Both the table pointer and the index are zero. So there is no entry
   to name: the lookup is not indexing past the end of a populated
   registry, it is dereferencing a registry pointer that was never
   populated. That moves the question from "which type failed to
   register" to "which global holds this table, and what was supposed to
   write it" -- a different search, and a narrower one.
