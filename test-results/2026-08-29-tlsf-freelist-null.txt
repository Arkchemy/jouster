ANSWERED, AND NOT AMBIGUOUSLY
-----------------------------
All six recorded nodes are 0. The free list head is NULL, and walking it does
this:

    r7 = 0
    r7 != r3 (control)      -> enter the loop
    r8 = *(0 + 4)           -> guest address 4
    r7 = *(0 + 8)           -> guest address 8, which is also 0
    r7 != r3                -> loop forever at address zero

So it is not a cycle among real blocks and not a merely long list. It is a
NULL head with no NULL check, spinning on address 0 because the guest-memory
mask makes address 0 readable instead of faulting. Third hang of this exact
shape today, after igStringPool::remove and the string-pool bucket walk.

The 1,000,000-iteration bail-out did its job: it tripped 375 times and the
boot kept running, taking execution from 150,839 calls to 392,874 in the same
run rather than costing another test cycle.

WHAT IT MEANS
-------------
The loop reaches this list only after the TLSF bitmap said the size class is
non-empty:

    21f0450: lwz r10, 0x10(r3)   ; first-level bitmap
    21f0464: cntlzw r5, r10      ; highest set bit -> fl
    21f0480: lwz r12, 0x14(r9)   ; second-level bitmap
    21f0490: cntlzw r10, r12     ; -> sl
    21f04b4: lwz r7, 0x74(r6)    ; free list head for [fl][sl]

Bitmap says occupied, list is NULL: the control block is internally
inconsistent. Either a bit was set without a block being linked in, or the
head was cleared without the bit being cleared. r4 and r5 (0x40/0x7 this run,
0x18/0xf last) are the size-class inputs, and they change run to run, so this
is not one specific poisoned class.

Registrations stayed at 61, so nothing new registered -- the allocator is
failing rather than the reflection system.
