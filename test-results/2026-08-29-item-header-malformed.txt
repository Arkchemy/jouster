bucketCount is 1024, matching the "expect 16384 and 1024" params logged at

TWO CORRECTIONS THIS SETTLES
----------------------------
1. item+0x00 is NOT the pool. It is the igStringPoolContainer -- the same
   pointer the pool itself holds at +0x14 -- which is why the callee is
   igStringPoolContainer::internalRelease and not an igStringPool method.
   Earlier notes in this session called r3 "the pool"; that was wrong.

2. A pooled string living above the module range is NORMAL. The real item's
   chars sit at 0x11bdb8d8, well above the image end 0x10181290, and the real
   game releases it happily. So "the string is above B" was never evidence of
   anything by itself.

WHERE THE BUG ACTUALLY IS
-------------------------
jouster's failing item:

    item = 0x44001f8   *(item+0) = 0x4400204 = item + 0xc

The container pointer field holds the item's own character buffer. Against the
healthy layout that is unambiguous: either the item was never initialised as
an igStringPoolItem, or 0x44001f8 is not an item at all and the code simply
subtracted 12 from a heap string that was never pooled.

THIS BUILD IDENTIFIES WHICH
---------------------------
Captures the four header words and the string itself on the first bad call:

    baditem: hdr=[0x..,0x..,0x..,0x..] str="..."

Compare against the healthy shape {container, 1, 0, chars}:

  - a plausible refcount/next and a readable string -> a real item whose
    container pointer was never written; the bug is in whatever allocates
    items
  - garbage words and an unreadable string -> not an item at all, and the
    question becomes where that heap string came from and why it reached a
    release path
  - a recognisable filename like the alchemy.xml above -> it can be traced
    directly back to its creation site
