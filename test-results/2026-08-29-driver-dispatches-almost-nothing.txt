A PROBE ERROR, FIRST
--------------------
maxlist=0 is not a finding, it is the probe being wrong. It read the list
count from r3+4 at the driver's ENTRY, but r3 there is igMetaObject*&, not the
list. The real code obtains the list by CALLING r4:

    215b958: mtctr r29        ; r29 = r4, the list-getter
    215b95c: bctrl            ; call it -- list returned in r3
    215b960: or. r26, r3, r3  ; NULL check
    215b964: beq 0x215ba84    ; nothing to walk, bail
    215b968: lwz r27, 4(r3)   ; count, from the RESULT

So the count had to be read after the call, not before. Recording this because
a zero from a probe pointed at the wrong register looks exactly like a zero
from the program.

WHAT IS A REAL FINDING
----------------------
    calls = 1,163      the driver runs 1,163 times
    n     =   318      it dispatches 318 entries in total

That is 0.27 entries per call. One retail list alone holds 21. So the
overwhelming majority of calls dispatch nothing at all, which is what happens
when the list-getter at 0x215b95c returns NULL and the beq at 0x215b964 bails
before any walking.

That fits the dispatch-miss counter exactly: 74,712 misses, every one to
addr=0x0. A NULL through mtctr/bctrl is silently ignored, the caller carries
on as if the call happened, and r3 still holds whatever it held.
