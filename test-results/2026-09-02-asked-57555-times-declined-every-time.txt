igArchive::startNewTasks is called 57,555 times and produced exactly one

constantly, and refusing every time.

That is the branch this build was written to distinguish, and it is the
first of the two:

    read hits=1, startNewTasks climbing    the archive keeps being asked and
                                           never issues another read -- the
                                           fault is in startNewTasks' own
                                           decision

setStatus froze at 8 hits early and never moved again, so the work item is
not being cycled. The last status written was 0x0 on item 0x4503760, which
is a different object from the work item handed to read (0x452cfc8) -- the
watch keeps only the last hit, so that is the last item touched rather than
ours.

WHERE THE DECISION IS MADE
--------------------------
startNewTasks loads a task list from a fixed global and walks it. Three
tests can end the walk without starting anything:

    2168930: cmpw  r25, r0        i vs [list+8]        list is EMPTY
    2168954: cmplw r30, r4        [e+0x14] > [e+0x18]  entry skipped
    2168964: cmpwi r3, 0          [e+8] == 0           entry skipped

From the translated prologue, the addresses are concrete:

    .bss+306380 = guest 421308    an owner pointer, passed to 0x216e230
    .bss+306384 = guest 421312    the task list
       [list+8]                   entry count
       [list+0x14]                entry array

Those three outcomes want opposite fixes. An empty list means nothing is
ever queued and the fault is upstream, in whoever should be appending work.
A non-empty list whose entries are all skipped means the work IS queued and
its cursor or pointer is wrong -- and the two guards then name which.
