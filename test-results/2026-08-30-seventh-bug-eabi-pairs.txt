THE BUG
-------
Not the shim's semantics, and not the carry idiom that reads its result --
ppc_addic and ppc_subfe both handle XER[CA] correctly, and the CAS body is
textbook. The argument registers were wrong.

PPC EABI passes a 64-bit argument in a register pair whose first register is
ODD-numbered: (r3,r4), (r5,r6), (r7,r8), (r9,r10). With the pointer in r3, the
first 64-bit argument SKIPS r4 and lands in r5:r6, and the second in r7:r8.

Every Atomic64 shim read r4:r5 and r6:r7 -- one register short. The retail
call site says so plainly:

    21d9e5c: lwz  r6, 4(r10)     low word of the current value
    21d9e60: lwz  r8, 0(r10)     high word
    21d9e68: mr   r5, r8         so r5:r6 is `compare`
    21d9e3c: andc r8, r6, r10    and r7:r8 is `value`

Reading r4:r5 made the comparand garbage, the CAS could never match, and the
retry loop spun forever.

Worth recording: the file's own header comment asserted "r4:r5 for the first
one after ptr in r3" and rated the CAS "high confidence". The confidence was
in the semantics, which were right; the ABI note beside it was wrong, and
every function in the file had been written to match the comment rather than
the ABI. Four shims fixed: OSAddAtomic64, OSAndAtomic64, OSOrAtomic64,
OSCompareAndSwapAtomic64.

Checked the rest: the only other 64-bit argument assembled from registers
anywhere in the shims is GX2WaitTimeStamp, whose u64 is the FIRST argument and
therefore correctly in (r3,r4). Return values in r3(high):r4(low) were always
right.
