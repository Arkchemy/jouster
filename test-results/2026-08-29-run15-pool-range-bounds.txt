So nothing "moved". The default pool pointer is correct and stable for the
whole run. releaseString is simply being handed a NULL (or garbage) `this`,
because the CONTAINER it comes from is garbage:

    igStringPoolContainer::internalRelease (21a583c):
        r5 = r3                      ; container
        r3 = load(container + 0)     ; pool = container->[0]
        b  releaseString             ; tail call

container = 0 -> load(0) -> pool = 0. (The tail call also explains why
caller_lr showed igStringRefList::setAll rather than internalRelease: lr is
not updated by a tail branch, so the probe reports the grandparent. Normal
PowerPC, not a bug -- I nearly filed it as one after reading a grep-filtered
view of the function that hid the emitted call.)

WHERE THE GARBAGE CONTAINERS COME FROM
---------------------------------------
igStringRefList::setAll guards each release with a range test:

    lwz   r0, 0xc98(r29)      ; lower bound  (.bss+306328, synthetic 421256)
    cmplw r11, r0
    blt   -> release path
    lwz   r4, 0xc9c(r28)      ; upper bound  (.bss+306332, synthetic 421260)
    cmplw r11, r4
    blt   -> skip
          -> release path

The release path runs when the item is OUTSIDE the pool's address range:
pooled strings are immortal and skipped, non-pooled ones get refcounted and
released. (My first reading had this inverted; the conclusion is the same but
the mechanism is not.)

With both bounds zero, `x < 0` is false for every unsigned x, so EVERY pointer
looks non-pooled and gets released -- including things that are not string
containers at all.

THE ONLY TWO WRITERS
--------------------
Scanning every reference to those addresses (401 and 398 of them) and matching
folded base registers to stores, exactly two stores exist in the entire tree,
both in Core::igCafeSystemMemory::__ct__:

    2156938: stw r10, 0xc98(r11)   ; lower
    2156958: stw r0,  0xc9c(r11)   ; upper

A plain grep for a literal address finds nothing here, because the address is
folded into a register first. That is worth remembering: on this codebase
"grep found no stores" is not evidence until the folded-base form is checked
too -- the same shape of mistake as the display-ownership grep earlier today.
