That resolves the fork the previous build was written to settle, and it
resolves it the opposite way to the reading offered last time:

    "nobody wants anything, look upstream"     WRONG

Work was produced. Three items were queued onto the list. The pump that
consumes them runs constantly. One read was ever issued. The producer side
is fine and the fault is in the entry state, not upstream of the archive.

Worth stating plainly because the previous write-up leaned the other way and
would have sent the next few days looking in the wrong place.

-----------------------------------------------------
    addWork's work item     wi = 0x4503700
    the stuck entry's +8    f8 = 0x4503700

They match. So the entry startNewTasks refuses to act on is holding exactly
the work item addWork queued. Nothing is lost, misrouted or dangling -- the
queue is correctly linked and simply never acted upon.

gamble.

A DEAD END, RECORDED SO IT IS NOT REPEATED
-------------------------------------------
Grepping the generated C for writes to +0x14 looked productive and returned
a dozen archive functions including asyncCallback, the completion handler.
It was wrong. Those matches are `stw rN, 0x14(r1)` -- register spills to the
STACK in function prologues, r1 being the stack pointer, not writes to any
object field.

Static search on an offset cannot distinguish a field write from a stack
slot at the same displacement. That is what the store watch is for.

Whoever writes those addresses gets recorded with the writing PC, the link
