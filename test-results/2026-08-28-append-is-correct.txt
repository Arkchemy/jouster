THE APPEND IS CORRECT, AND THE NULL MAY NOT BE A FAULT

igHandlePool does get its field list built -- the probe fires once with a
real metaobject. Reading the argument set-up shows the call is entirely
well-formed:

  21b1b7c: lwz  r31, 0x4cac(r31)   metaobject from .bss
  21b1b80: addi r4, r4, -0x2138    instFuncs array
  21b1b84: li   r5, 0              start index
  21b1b88: li   r6, 2              count: both fields

So the sixteen-classes-without-field-lists guess from the previous run
was wrong, and it is as well it was measured rather than believed.

More importantly, _freeHandle=0xffff is now explained. Its metafield is
an igIntMetaField and arkRegisterInitialize calls setDefault on it, so
0xffff is a DEFAULT VALUE applied at construction, not evidence of
successful initialisation. _handleList is an igObjectRefMetaField, and
the default for an object reference is null.

That reframes the whole thing: a null _handleList immediately after
construction may be completely normal. The fault would then be that
igHandlePool::setCapacity runs before whatever is supposed to populate
it -- an ordering problem, not a missing-construction one.
