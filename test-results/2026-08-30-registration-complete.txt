THE LIKELY CAUSE, AND A REAL BUG FIXED REGARDLESS
-------------------------------------------------
cafeos_coreinit_atomic.h opened with this justification:

    "Atomic" only matters when something else could run between the read and
    the write -- this runtime has exactly one PpcContext executing
    sequentially (no threads), so a plain read-modify-write is genuinely
    atomic here, not just a shortcut standing in for one.

That was true when written. It is not true now: OSResumeThread calls
pthread_create, so guest threads are real host threads sharing one
PpcSharedMemory. Every function in that file was an unsynchronised
read-modify-write on memory two threads touch at once -- and a lock-free job
queue is precisely what leans on those being atomic.

Fixed by taking one mutex across each operation. Two details worth stating:
the lock is weak rather than static, because a file-scope static in a header
of static inline functions gives every translation unit its own lock and would
serialise against nothing; and a single global lock is coarse, but these are
rare calls on a handful of words and correctness under real threads is the
entire point of the function.

Whether that is the stall is not yet established -- it is a real defect found
while investigating it, and the sort that produces exactly this symptom.
