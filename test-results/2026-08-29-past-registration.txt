TWO CORRECTIONS
---------------
1. igFile was never missing. The only static table containing its arkRegister
   address is referenced by exactly one function,
   arkRegisterInternal(igIGBFile), and igIGBFile is retail #127 while the boot
   reaches #125. Registration is recursive, so dependencies fire before their
   owner -- which is why the retail log has igFile at #80 and its owner at
   #127. It was beyond the frontier, not skipped. It had been probed for
   across several builds and reported as missing.

2. "Our dependency lists are built short" is also wrong, and for the same
   reason. maxlist=11 against a retail 21 compared our numbers to a retail
   measurement taken at a point in the boot we have not reached; the 21-entry
   list is igIGBFile's.

Both mistakes share one cause: ground truth captured at the wrong point in the
boot. Cemu makes it easy to measure the retail game anywhere, which makes it
easy to measure it somewhere that does not correspond to where we are.

So the real picture: 124 of the retail first 125 register, in exactly the
retail order, no holes.

DISCORD CORROBORATION
---------------------
From the existing local exports, not by scraping. NefariousTechSupport, who
did the original Alchemy reverse engineering:

  #findings           "it does a call to Core::igArkRegister, passing the class
                       name, metaobject pointer, parent class' arkRegisterInternal
                       function, type size, and vtable pointer"
  #igarchiveextractor "The game uses it to turn all the type indexes into the
                       corresponding vtables"
  #igcauldron         "All objects have a virtual function called getMeta, that
                       returns a pointer to their igMetaObject"

The second is the mechanism this project spent a day inside: setCapacity reads
a metaobject from a global, takes its type index at +0xc, and indexes a table.
The first independently confirms the inheritance-chain recursion that the Cemu
capture showed.

alchemy.xml, the first file the retail engine opens, turns out to be plain
configuration -- Gfx vramBSize 419430400, tripleBuffer true, Sg traversal block
sizes, and Tfb startLevel "Title". No class list, so it does not drive
registration.
