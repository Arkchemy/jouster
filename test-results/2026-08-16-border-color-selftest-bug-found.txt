Screen showed RED -- 42/43 self-test checks passed, 1 real failure:
[GX2SetPixelSamplerBorderColor changes the real bound descriptor]
got=0 want=1 -- FAIL.

Real root cause (fixed in commit 70f03a7, immediately after this run):
a bug in the self-test itself, not the shim. GX2SetPixelSamplerBorderColor's
real signature takes its index argument in r3, but the test had
r3=0x5000 (copy-pasted from the adjacent GX2SetPixelSampler/
GX2InitSamplerBorderType calls, which DO take a sampler pointer there)
instead of r3=0, the real index. Since 0x5000 is far outside the real,
bounded sampler-slot range (0-17), the shim's own real bounds check
correctly and safely no-op'd both border-color-set calls in the test --
meaning the real shim behaved exactly as designed (rejecting a bogus
out-of-range index) and this test bug never actually exercised the
real border-color decode logic at all. That logic was already verified
separately, correctly, by a standalone host test written when
GX2SetPixelSamplerBorderColor was first implemented.

This is a real, valuable finding from actually running on hardware --
exactly the kind of self-test authoring mistake that's easy to miss
reading the code but immediately visible as a real, unambiguous FAIL
on a real device. Confirms the self-test's own red/green signal and
FAIL reporting work correctly end to end, not just the happy path.

All other 42 checks passed, including the real, newly-added
GX2CalcSurfaceSizeAndAlignment hardware checks (LINEAR_SPECIAL and
LINEAR_ALIGNED cases, both exact matches). GX2SetColorBuffer's own
checks aren't in this run -- they were added in a later commit
(f82b17a), after this test build.
