WHAT THE ONE REGISTRATION ACTUALLY WAS
--------------------------------------
r4 is the path argument. Reconstructing .rodata at 0xb7490 (750,736) gives:

    'ram:/tfbGameIGX.igx'

and r5 = 0xb751c = 750,876 is exactly the address of the embedded document
that begins `<igx name="tfbGame">`. The argument mapping is confirmed by two
independent addresses, so this identification is not a guess.

So the single call registers the game's IGX, **not the engine config**.
ram:/alchemy.xml is never registered.

THE INFERENCE THAT WAS WRONG
----------------------------
igJobQueue::start sits LATER in that same function, at 2148604, and it fired
at call 204,133 -- while the only addReadOnlyMemoryEntry came at 1,599,789.
Those cannot both belong to one linear pass through igArkCore::init.

So igJobQueue::start was not called from igArkCore::init. It was reached
indirectly. generated_0136.c holds the guest-address-to-function table that
every bctrl resolves through, and igJobQueue::start, init, setMemoryPool,
jqAttachQueueToWorkers, jqFlush, jqWorkerLoop and the rest are all in it.

I had treated "igJobQueue::start fired" as evidence that igArkCore::init ran.
It never was. It only ever proved that something called start.

WHAT THIS PUTS BACK ON THE TABLE
--------------------------------
The 2026-08-29 write-up recorded plainly: "igArkCore::init has never run, so
nothing has yet opened a game file of any kind." I assumed that had been
superseded by later progress. The addReadOnlyMemoryEntry count says it may
not have been.

If igArkCore::init has still never run, then today's entire chain -- the
decompression job, the job queue, the worker sleep loop, the archive task
cursor -- are all downstream symptoms of an engine that was never
initialised, not separate defects. The archive can still open a file and
issue reads because those go through paths that do not require ArkCore init;
what they cannot do is complete work that needs a configured engine.
