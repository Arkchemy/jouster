WHAT THE STATIC SEARCH SAYS, AND WHERE IT RUNS OUT
--------------------------------------------------
Following the chain by address:

    arkRegister_X -> takes &arkRegisterInternal_X
    arkRegisterInternal_X -> takes &arkRegisterInitialize_X

Every level, for the missing classes and the working control alike, exists in
the output and is reachable only through ppc_dispatch. No direct call to any
of them exists anywhere in 8.7 million lines.

Then the trail stops, and this is the interesting part:

    &arkRegister_igStorageDevice  materialised in code : 0 places
    &arkRegister_igFile           materialised in code : 0 places
    either value stored by ppc_init_globals            : 0 times

Neither pointer is produced by any instruction, and neither is written by the
globals initialiser -- yet the control is demonstrably entered. So the driver
obtains these addresses by some route the static search does not cover:
raw .data bytes copied one byte at a time by init_globals (which is how
section content is loaded, so a value-level grep cannot see it), a vtable
slot, or a computed address.

Rather than widen the static search again -- three of the searches in this
session have been defeated by exactly this kind of blind spot -- the control
is now asked directly.
