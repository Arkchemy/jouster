WHAT THE CEMU COMPARISON KILLED
  _decompressJobFlag was NOT the gate. Retail reads 0x0 in [task+0x14] on
  every sample, with _state=1 throughout -- identical to ours. Several runs
  were built around that field being the thing that never gets set; it never
  gets set on the working system either. Comparing against the system that
  works retired the theory in one run.

WHAT ACTUALLY DIFFERS -- the per-file parent object ([task+8])
                 retail                        ours
  +0x18 total    33, then 8 for the next file  0
  +0x14 cursor   1 -> 7 -> ... -> 34           1
  +0x1c outstanding  set to 33, drains to 0    1
  Retail passes through 1/0/1 for exactly one sample on its way in. Ours is
  parked in that pre-count transient forever: no count, nothing to issue,
  the outstanding counter never drains, updateTasks takes the skip branch
  every time.

THE MECHANISM, MEASURED ON HARDWARE
  ARCHQ  parent +0x14=1 +0x18=0 +0x1c=1
         completion gate hits=1 zero=1 [batch+8]=0x0 [batch+4]=0x0
  jqWorkerLoop reached its completion gate once in 25,200 frames and skipped
  it, because [batch+8] is zero. jqAddBatchToQueue sets [batch+8] from
  [module+4]. So the whole stall reduces to one word.

METHOD NOTE
  Reading the folded C, not the disassembly comment, mattered again here:
  lis+addi and even stwu displacements are folded into the register
