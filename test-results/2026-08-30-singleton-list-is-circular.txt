    0x6b640 -> 0x6b670 -> 0x6b658 -> 0x6b688 -> 0x6b690 -> 0x6b640

7,630 laps in one traversal. The loop is `while (node) construct(node)`, and a
circular list never reaches null.

Repeated node ADDRESSES, not distinct nodes with equal payloads -- so this is
a corrupt link, not a list holding duplicates. Of the two shapes the probe was
written to separate, it is the first.

Every fold is correct, including the stwu whose displacement is folded into r7
(and whose register update is then a no-op, which is why dropping it is safe
here).

Run once from a zero head this is an ordinary prepend ending in null. Run a
SECOND time and A.next is set to whatever the head has since become -- a node
already in the list -- and the list closes. The observed ring is exactly the
shape a second pass produces, with the nodes from the later initializer
(0x6b640, 0x6b670, 0x6b658) sitting in front and A pointing back at them.

Nothing writes these next fields statically: no store to 439876, 439900,
439924, 439948 or 439956 exists anywhere in ppc_init_globals. They are built
at runtime, so this is about how often the code runs, not about the image.
