THE HYPOTHESIS, AND WHY IT IS ONLY THAT
---------------------------------------
The archive header that landed correctly in guest memory reads:

    49 47 41 1a   "IGA\x1a"
    08 00 00 00   version 8
    6a 00 00 00   106 files

If [e+0x18] is meant to hold a file or chunk count, 106 is what it should
hold, and it holds 0. That would make this a header that was read but never
parsed into the object that needs it.

That is a hypothesis built on a field offset nobody has confirmed. +0x14 and
+0x18 are only known to be a cursor and a limit because of how startNewTasks
compares them. Calling them "files processed" and "file count" is a guess,
and this project has a long history of guesses about field meanings costing
a hardware round.
