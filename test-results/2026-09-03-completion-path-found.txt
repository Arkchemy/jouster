THE DECODE THAT MADE THIS READABLE
----------------------------------
NefariousTechSupport/igRewrite8 (Apache-2.0) is a C# reimplementation of the
Alchemy runtime, not just its file formats. It names what were raw numbers:

    Status:   kStatusInactive=0 kStatusActive=1 kStatusComplete=2
              kStatusDeviceNotFound=3 kStatusInvalidPath=4 ...

The byte at [workItem+0x23] is the LOW BYTE of a u32 _status at +0x20 --
PPC is big-endian, so a 4-byte enum is read with lbz at +3. Every observed
value lands on a real name.

So st1 = 1 = kStatusActive. igArchive::updateTasks keeps the entry BECAUSE
its work item is still active. It has been behaving correctly the whole
time. The question was never "why does it not reap".

THE ONE WORD THAT BLOCKS IT
---------------------------
    2168204  bne   0x2168218     [updq entry+0x14] != 0 -> other work
    2168208  lwz   r9, 0x1c(r17) r17 = archq entry 0xf7d05ec, [+0x1c]
    216820c  cmpwi r9, 0
    2168210  bne   0x216852c     non-zero -> SKIP
    2168214  b     0x2168348     zero    -> COMPLETE

[updq entry+0x14] measured 0, so the first branch is not taken. Then
[archq entry+0x1c] measured 1, so the second branch IS taken, and control
goes to 0x216852c -- which is nothing but the loop decrement:

    216852c  addic. r15, r15, -1
    2168530  addi   r22, r22, -4
    2168534  bge    0x2167c60      next entry
    2168538  ...                   epilogue

**If [archq entry + 0x1c] were 0, the work item would be completed.** It is
1, every frame, and that single word is the entire blockage.

The archq entry's three interesting words, for the record:

    +0x14 = 1   the cursor startNewTasks compares
    +0x18 = 0   the limit (correct: serialised reader, one task in flight)
    +0x1c = 1   gates completion            <- the live one

Reading them together, +0x1c looks like outstanding-reads: one read was
issued and nothing ever counted it as finished. The FS side says the read
DID finish -- ard=1/131072, res=1, cb ok=1, IGA magic in the buffer -- so
the suspicion is that our async completion never decrements this counter.
That would make it our bug, in the shim, not the game's.
