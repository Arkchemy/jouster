WHAT THE TIMING SAYS
--------------------

seconds -- against sig=2 and wake=1. That is the signature of threads
parked in a timed sleep that keep expiring and finding nothing, rather than
threads blocked forever. They are alive and looking.

The batch was submitted at call 1,610,868. The workers have been looping
since call ~204,169. So they were awake and polling for the whole window in
which the work existed, and still never ran it.

That makes the leading explanation a VISIBILITY problem rather than a
scheduling one: jqPopNextBatch does not find the batch that addBatch added.
Either it is looking at a different queue than the one addBatch filled, or
the write is not visible to the worker threads.

NOTE ON THE COURIER
-------------------
This round's push failed three times. The Switch had re-enumerated on USB
(device 046 -> 054) while gvfs kept the old instance, so the mount
directory still existed but every operation hung. The courier's
"is it mounted" test was `[ -d "$GV" ]`, which a stale mount passes.

Fixed: every gio call now has a timeout, presence is probed with an actual
list rather than assumed from the directory, and after three failures the
courier clears the gvfs mtp backend and remounts itself. The self-heal uses
pkill -x, never -f -- `pkill -f gvfsd-mtp` matched its own command line and
killed the shell during this debugging, which is the fourth time that
specific mistake has been made in this project.
