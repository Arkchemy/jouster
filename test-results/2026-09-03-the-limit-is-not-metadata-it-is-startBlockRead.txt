2026-09-03 — the limit is not metadata; the candidate is startBlockRead
========================================================================

Two things settled without a hardware round, using tooling this project
already had.

THE FIELD IS NOT REFLECTED
--------------------------
blaster's extract_field_schema.py reads the compiler-generated
arkRegisterInitialize functions straight out of the recompiled C and reports
each class's registered fields. For the class in question:

    "Core::igArchiveWorkItem": [ { "name": "_fileWorkItem" } ]

One reflected field. Not two, not twelve. And that field is the entry's +8 --
the 0x4503700 that addWork was handed and that the entry carries.

So +0x18 is a PLAIN member, not a reflected one. igMetaObject::createInstance
stamps the vtable and initialises reflected fields; a plain member is left as
the allocation found it, which is zero.

That kills the hypothesis from the previous build outright. The metaobject
being fully populated was not the point: even a perfect metaobject would
never set this field, because the field is not in the schema.

Neighbouring classes are the same shape -- igArchiveBlockTask has _parent,
igArchiveBlockManager has _blocks, igArchiveBlock has _owner. One reflected
field each. This engine reflects the object graph, not the scalars.

SO SOMETHING MUST SET IT IN CODE
---------------------------------
And that code is in our binary, because it is the same translation. The
candidate:

    igArchive::startBlockRead(igFileDescriptor*, void*, uint, uint)  0x2168550
    2168680: stw r24, 0x18(r30)

It is the only clean writer of +0x18 in the archive code that is not a stack
spill, and "start block read" is exactly the shape of thing that establishes
a byte budget for a transfer.
