WHY THE ARGUMENT WAS WRONG
--------------------------
I enumerated every label and branch in the 0x21682xx region and concluded
the decrement at 21682e0 was reachable only via 0x2168218. That part holds.
But there is a SECOND decrement, at 2168164, in the 0x21681xx region --
which I never enumerated. It is reached from:

    2168068  beq 0x216815c

and 0x2168060 is the target of the st2 test:

    2167d40  cmpwi r4, 2           st2 == kStatusComplete
    2167d44  beq 0x2168060

So the second decrement was live early in the run, exactly as the 11 writes
show. Checking half a region and generalising was the error.

THE LATCH
---------
    2168144  lwz   r9, 0x1c(r17)
    2168148  li    r6, 1
    216814c  cmpwi r9, 0
    2168150  stw   r6, 0xc(r16)     [updq entry + 0xc] = 1   UNCONDITIONAL
    2168154  bne   0x216852c        +0x1c non-zero -> skip
    2168158  b     0x2168348        +0x1c zero    -> COMPLETE

That store is unconditional. Once it runs, [updq entry+0xc] is 1 forever,
and back at the top of the loop:

    2167d20  cmpwi r11, 0          r11 = [e+0xc]
    2167d24  bne   0x21681cc       -> now always taken

so the whole 2167d28..2167d44 branch -- including the route to the second
decrement -- is permanently unreachable. The engine reached 2168144 while
+0x1c was still non-zero, latched [e+0xc] to 1, and skipped. From then on
the only route forward is 21681cc, which needs [updq entry+0x14] != 0.

That matches the timing exactly: the 11 writes stop at call 1,610,587 and
never resume, while the run continues to ~3.9M calls.

WHAT SURVIVES
-------------
The chain's conclusion is unchanged, and now better supported:

    [updq entry + 0x14] == 0  ->  21681cc path cannot progress
                              ->  ageBlocks / the 21682e0 decrement never run
                              ->  [archq+0x1c] stuck at 1
                              ->  completion at 0x2168348 never runs
                              ->  work item stays kStatusActive
                              ->  updateTasks correctly keeps the entry
                              ->  cursor never released
                              ->  startNewTasks skips ~57,000 times

What changed is the mechanism by which the alternative routes closed: not
"they were never reachable" but "they were reachable, ran, and a latch shut
them". That is a better explanation because it accounts for the 11 writes
instead of contradicting them.

METHOD NOTE
-----------
Writing the prediction down is what made this round productive. A wrong
prediction that is checked costs one run and buys a real mechanism; a wrong
belief that is never stated survives for four rounds, which is exactly what
happened with "nothing sets the limit". Enumerate the whole region, not the
half that contains the answer you expect.
