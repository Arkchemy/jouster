2026-08-29 — computed jump tables (switch statements) are not translated
========================================================================

THE FINDING
-----------
ExpandPlane, Bink's plane decompressor, dispatches its bitstream opcodes
through a classic PowerPC jump table:

    2379acc: lbz    r7, 0(r9)      read opcode byte
    2379ad0: cmplwi r7, 9
    2379ad4: bgt    exit           bounds check, 0..9
    2379ad8: slwi   r7, r7, 2      opcode * 4
    2379adc: addis  r8, r7, 0x238  table base 0x2379AEC
    2379ae0: addi   r8, r8, -0x6514
    2379ae4: mtctr  r8
    2379ae8: bctr                  jump INTO the table below
    2379aec: b 0x2379b14           <- table entry 0
    2379af0: b 0x2379bbc           <- table entry 1
    2379af4: b 0x237a7f4           <- ...

conquertron emits that as:

    ctx->r[8] = ctx->r[7] + 5229660u;   /* &.text+3644108 */
    ctx->ctr  = ctx->r[8];
    ppc_dispatch(ctx, ctx->ctr);
    return;

Two independent faults, either one fatal:

1. bctr is treated as an indirect CALL followed by a return. Here the target
   is an address INSIDE the same function, so the correct translation is a
   computed goto, not a call.
2. The table base is folded to a SYNTHETIC .text address (5229660), while
   ppc_dispatch's switch is keyed by REAL guest addresses (0x2379AEC =
   37198572). Verified: none of 0x2379aec/0x2379af0/0x2379af4 has a dispatch
   entry.

ppc_dispatch has no default case, so an unresolvable address falls off the end
of the switch and returns silently. The generated `return;` then abandons the
function. A switch statement compiled to a jump table therefore does nothing
at all and exits its caller -- silently, with no stub, no log, and no crash.

WHY THIS MATTERS BEYOND VIDEO
------------------------------
This is not a Bink problem. Any function in the game whose switch the GHS
compiler turned into a jump table has the same hole, and bitstream decoders,
state machines and message handlers are exactly where such switches live. It
belongs in the same family as the two instruction-level bugs found earlier
today (record-form CR0 across 6745 sites, srawi's missing XER[CA] across
2890) but is structural rather than per-instruction.

HOW IT WAS REACHED
------------------
A chain of eliminations, each by measurement:
  registered planes stayed zero          -> registration is unconditional
  BinkDoFrame returned 0, not 1          -> not "frame skipped"
  file reads climbed 10 -> 14            -> not starved of data
  75 guest calls                         -> no decoding was happening at all
  frame advanced before decode           -> 2589 calls, decoding starts
  four loops instrumented, all silent    -> not looping where I thought
  last_pc is the last function ENTERED   -> the spin is in the CALLER
  29 back-edges instrumented in ExpandPlane -> EXPAND_SPIN_2379aac fires
  r30 climbing 8 bytes/iteration into the stack region -> runaway pointer

MY OWN ERRORS ALONG THE WAY, RECORDED
--------------------------------------
- Read last_pc as "where the thread is now". It is written at function entry,
  so it means "last function entered". Those differ exactly when a function
  returns and its caller loops, which was this case, and it cost two runs.
- Instrumented one loop of four on the assumption it was the obvious one, and
  read the resulting silence as information rather than as a mis-aimed probe.
  Third time today.
- Nearly added a duplicate ppc_sraw helper; the existing one was already
  correct and better than the replacement.

WHAT A FIX LOOKS LIKE
---------------------
conquertron needs to recognise the idiom: mtctr fed by a base+index where the
base resolves inside the current function, then bctr. The table entries are
already recovered as labels, so the emission should be a switch over the
computed index mapping to `goto L_<target>` -- not ppc_dispatch. The bounds
check immediately above (cmplwi r7, 9; bgt) even gives the table length.

Also worth doing regardless: ppc_dispatch should have a default case that
logs the unresolved address instead of returning silently. Every one of these
has been invisible.
