WHY THE NULL IS NOT THE BUG
---------------------------
The caller is Core::igObjectHandleManager::userInstantiate(bool):

    21501d4: bl   igDataList::setCapacity
    21501e4: bl   igHandleRedirectPool::instantiateFromPool
    21501e8: stw  r3, 0x2c(r28)
    21501ec: lwz  r8, 0x18(r3)     ; the new pool's +0x18
    21501f0: cmpwi r8, 0
    21501f4: bne  0x2150220        ; non-zero -> the normal path
    2150204: li   r7, 0            ; else pool = 0
    2150208: bl   igPool::activate

`li r7, 0` is a hardcoded literal in the game's own code. Passing null to
activate is deliberate, on a branch taken only when the freshly created pool's
+0x18 reads zero. The real game takes the other branch.

So four rounds of "find the null" were chasing a value the binary sets on
purpose. The actual fault is that +0x18 is zero on an object that was just
instantiated.

WHERE THAT LEADS
----------------

whose type-index lookup was broken earlier today and was fixed by reading the
real value (2) off the retail game in Cemu. This lands back in the same
machinery, one layer along.
